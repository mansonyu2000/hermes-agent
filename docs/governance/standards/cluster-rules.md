# 功能集群治理规则

> 最后更新: 2026-07-22 | 由 Orchestrator + 人类共同维护

## 核心原则

1. **功能聚拢，不技术分层** — 一个集群 = 一组用户能感知的关联功能。不是按"前端/后端/数据库"分，是按"用户要做什么"分。
2. **灵活归并** — 细功能可并入已有集群做迭代增量，集群过大可拆。每次归并/拆分由 Orchestrator 提案，人类确认。
3. **每次操作必留文档** — 不可逆操作不做盲区。

## 集群判定标准（Orchestrator 在阶段1-2 执行）

| 条件 | 阈值 |
|------|:--:|
| 共享数据模型 | 同一集群操作同一组核心表 |
| 共享 UI 入口 | 同一集群的页面在同一导航路径下 |
| 可独立测试 | 集群做完后能独立跑验收测试 |
| 可独立交付 | 集群做完后能独立上线 |
| 工作量 | 2-8 周（超出则拆，不足则并） |

## 集群生命周期操作

| 操作 | 触发条件 | 谁来执行 | 必须产出 |
|------|---------|---------|---------|
| **新建** | 新功能启动，不属于任何已有集群 | Orchestrator | `docs/{cluster}/requirements/` 完整文档 |
| **归入** | 小功能(<2周)属于已有集群 | Orchestrator 提案 → 人类确认 | 在已有集群 `plan/` 中增加迭代任务 |
| **拆分** | 集群过大(>8周) | Orchestrator 提案 → 人类确认 | 新集群完整文档 + 原集群文档更新 |
| **合并** | 两个集群共享数据模型越来越重叠 | Orchestrator 提案 → 人类确认 | 合并后的统一文档，废弃旧集群目录（不删，标 `archived`） |
| **废弃** | 功能下线 | 人类确认 | 集群目录标记 `status: archived`，不删除 |

## 不允许的操作

- ❌ **无声变更** — 修改集群边界不写文档
- ❌ **跨集群引用代码而不声明** — 集群A依赖集群B的代码 → 必须在两个集群的 `architecture/` 中写明依赖关系
- ❌ **删除历史文档** — 废弃集群标 `archived`，不删文件
